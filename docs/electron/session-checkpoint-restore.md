# Session Data Checkpoint and Restore

English | [中文](session-checkpoint-restore.zh.md)

> The mechanism described here is implemented in `apps/electron/src/checkpoint/`; [Mechanism facts](#mechanism-facts) records the upstream behavior it builds on. The [Agent Note](../../.agents/notes/implemented/feature/2026-10-18-session-checkpoint-restore.md) owns the design rationale and the open follow-ups.

## Summary

Rivetdeck and CLI `dsh --profile web` share one `$DSH_HOME`, so sessions written by a newer harness can become unreadable to the older bundled Harness. Desktop stages a checkpoint after each reported clean exit and promotes only sessions that pass the bundled Harness's real read path, plus an on-demand per-session restore implemented as a journaled transaction under the session's own write lease.

## Background

The Desktop application supervises a Harness Host on the shared `web` profile: `apps/electron/src/main.ts` resolves `harnessHome` from `DSH_HOME` or `~/.dsh`, and `apps/electron/src/host.ts` boots the profile at `$DSH_HOME/profiles/web`. CLI `dsh --profile web` opens the same home. Both sides read and write the same session store, profile composition, settings, credentials, and KV storages, while `$DSH_HOME/electron/` stays Desktop-private.

A newer CLI release can therefore write data the bundled Harness cannot read. Without a checkpoint the only recovery is opening the affected data on a newer host, as recorded in the incident report that motivated this mechanism (dsh-plugin-git PR #20: `job/registered` at seq 24 inside `session.v4.jsonl.zstd`). [Sharing the Harness Home](shared-dsh-home.md) describes the current user-facing behavior.

<a id="mechanism-facts"></a>

## Mechanism facts

**Shared-home layout.** Sessions live under `$DSH_HOME/sessions/<project-key>/<encoded-session-id>/`, configured by `root: dshHomePath('sessions')` in `packages/bundle/base/cordis.patch.yml`, outside every profile. The managed profile file set is `package.json`, `cordis.patch.yml`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `compatibility.json`, plus installed `node_modules` (`packages/boot/plugin-manager`); the home-root `cordis.patch.yml` composes above the profile patch (`profile-context.ts` in `app-boot`). Current Settings values live inside the profile patch; a home `settings.yaml` is only a legacy one-time import renamed to `settings.yaml.imported`. KV domains live under `$DSH_HOME/storages/`; attachments under `$DSH_HOME/attachments/v1` are content-addressed.

**Generation-addressed immutable logs.** Each Session directory carries one file per format generation — `session.jsonl.zstd` for v0, `session.vN.jsonl.zstd` for later generations (`packages/session/session-format/src/filename.ts`). A newer writer migrating a log publishes a successor file and never edits the committed predecessor. Historical reads can pull related sessions: the v3→v4 migration collects descriptors of subagent children via `header.parentSession` (`catalog-migration.ts` in `session-persistence-jsonl`), so the read unit of one session is the session plus its related sources, not one directory in isolation.

**Admission rules.** `resolveGenerationInDirectory` selects the numerically highest canonical file with no fallback to earlier generations (`packages/session/session-persistence-jsonl/src/index.ts`). Header admission rejects `storedVersion > SESSION_FORMAT_VERSION`. Event admission (`validateStoredEvents` in `packages/session/session-persistence/src/storage-contract.ts`) rejects any event type outside `KNOWN_SESSION_EVENT_TYPES` unless the envelope carries `ignorable: true`. Listing skips sessions whose header is rejected; event admission runs only when a session is opened, so a listed session can still fail to open.

**Write leasing, per platform.** Each Session directory holds a `session.lock` that refuses a second concurrent writer (`SessionAlreadyOwnedError` in `lease.ts`). On POSIX the lease is a flock bound to the lock file's inode — it follows a renamed directory, so replacing the directory changes lock identity. On Windows it is a `Local\`-prefixed semaphore named by a hash of the resolved path — it survives inode replacement but holds no file handle, so open handles block renames while the semaphore itself gives no read isolation. Reads take no lease at all: header reads and listing never acquire `session.lock`, so a foreign reader can observe a Session directory mid-transaction. No home-wide "harness running" lock exists.

**Shutdown is not self-certifying.** `prepareToInstall` in `apps/electron/src/main.ts` stops the supervised Host through `stopHarness` (a private IPC request, 5 s grace, then SIGKILL in `harness/process.ts`; SIGTERM remains the fallback for children without IPC), and `stopHarness` resolves after a kill exactly as after a graceful exit. The Host's `createProcessShutdown` (`host.ts`) force-exits with the caller's code even when dispose fails or times out, and the startup-failure path reaches `prepareToInstall` as well. On the graceful path the persistence backend's teardown effect closes every open handle and close drains the append buffer (`storage.ts` in `session-persistence-jsonl`) and the Host records its drain outcome before exiting; Main merges the observed exit result afterward.

<a id="failure-modes"></a>

## Failure modes

| # | Trigger | On-disk result | Symptom in the older harness | Recoverable without a checkpoint? |
| - | ------- | -------------- | ---------------------------- | --------------------------------- |
| A | Newer harness has a higher format version and publishes `session.vN` | New successor file; predecessor intact | Session silently disappears from the list | Yes — removing the newer file exposes the predecessor, minus post-migration events |
| B | Newer harness shares the format version but writes event types the older build does not know | The committed current-generation file is polluted in place | Session stays listed; opening fails with a history-load error (`SessionFormatUnsupportedError` → `SESSION_QUERY_PERSISTENCE_FAILED`) | No — no pre-image exists |
| C | Newer harness edits the shared profile composition | `cordis.patch.yml` / `package.json` / `compatibility.json` / `node_modules` drift | Host boot can fail before any session opens | Case by case |

Mode B is the reported incident: `0.2.1-alpha.3` added `job/registered` and `job/settled` to `KNOWN_SESSION_EVENT_TYPES` as required (non-ignorable) events while `SESSION_FORMAT_VERSION` stayed 4, so an older build reading the same `session.v4.jsonl.zstd` refuses the whole log. Mode B is also the only cell where a checkpoint is the sole remedy: no untouched file remains to expose.

<a id="design"></a>

## Design

**Checkpoint cadence and promotion.** A checkpoint candidate is staged after a *reported* clean drain (below), into `$DSH_HOME/electron/checkpoints/<timestamp>.tmp/`, then committed by rename. Promotion is per session: each copied session — with its related-source closure — must pass validation through the bundled Harness's real read path (decompress, header admission, event admission, and the historical-migration path including related-source reads), executed read-only and cancellable in a separate child process, never synchronously in Main and never through a write-open that could publish. A session whose new copy fails validation keeps its previous verified copy; because this mixes capture times inside one checkpoint, the combined related-source closure is re-validated before the candidate commits. A retained session omitted by backend listing fails this second pass just as an explicit read failure does. Verification is validator-bound: after an app upgrade or downgrade, stored verified marks do not carry over, so a copy is re-validated under the current build at restore time as well. Retention protects the last verified copy per session and checkpoints referenced by queued restores or intent journals; an unreadable journal or a pending-queue file-read failure suspends pruning because the checkpoint references are unknown.

**Capture cancellation.** The 120-second capture deadline is checked during copies, validation, and staged-directory traversal, including immediately before the publication rename. File copies use an abort-aware pipeline that closes both streams before rejecting. Validation cancellation sends SIGTERM immediately, escalates to SIGKILL after two seconds if needed, and waits for worker stdio to close; an already-cancelled request starts no worker. Cancellation before publication discards the candidate and preserves committed checkpoints. Once rename publishes the checkpoint, its parent-directory flush completes and the outcome remains committed; cancellation skips or stops retention. An in-flight filesystem call and post-publication durability work can outlast the deadline.

**Shutdown reporting.** `stopHarness` resolving proves only that the child is gone. The Host must emit an explicit shutdown report — reached-ready plus drain/dispose outcome, distinct from its exit code — and Main must record signal, timeout, kill, and exit result. Promotion requires both the report's success and per-session validation; a failed boot never promotes, and an unreadable session encountered at open cannot replace its verified copy during relaunch. v1 fixes the conservative rule: an unverifiable run promotes nothing, and validating files from a killed run is left to later discussion.

**Manifest.** `manifest.json` records the checkpoint identity, the shutdown report's outcome, per-file source state `{path, size, mtimeNs}` captured at copy time, per-file copy digest `{size, hash}` bound to the bytes actually copied, and per-session `{dir, header, capturedAt, sourceCheckpointId, validator}` where `header` is the stored session header (it derives the related-source closure and re-acquires the write lease on resume) and validator is the app version and `SESSION_FORMAT_VERSION` that verified the copy. stat-diff compares live files against the recorded source state — a scan hint that detects foreign writes but proves neither writer identity nor copy integrity; the digest guards the copy itself, and per-session timestamps keep the confirmation UI honest when one checkpoint mixes captures from different exits. Carried files always compare live bytes against the saved digest, even when the recorded source stat matches: that source already failed validation.

**Covered set.** `sessions/` (required), `profiles/web/{cordis.yml,cordis.patch.yml,package.json,pnpm-workspace.yaml,pnpm-lock.yaml,compatibility.json}` (backup included in v1; see restore scope), the home-root `cordis.patch.yml`, `storages/session_projcache*` (rolled back with sessions), and `.env` (small, defensive). Excluded: `session.lock`, `session.migration.*.tmp`, `storages/*.lock` (transient), `attachments/`, `cache/` (content-addressed or regenerable), `node_modules` (rebuilt by the profile-restore transaction), credentials and identity files, `settings.yaml*` (legacy import only), and `electron/` itself. Checkpoint copies are cold archives and are never mounted as live harness storage.

**Detection.** Three layers: (1) at startup, manifest stat-diff plus a `session.vN` filename scan for N above the bundled version (mode A); hits then confirm through the same read-only validation used for promotion, in a worker, because compatible foreign writes also drift. (2) At open-time, `SessionFormatUnsupportedError` prompts restore in place — the only signal covering in-place pollution that slipped past detection. (3) A manual menu/tray entry. Startup and manual confirmation acquire every candidate's stored related-source write leases before validation and hold them through the worker read; contended or headerless closures are skipped, so an append followed by rollback cannot leave a stale refusal. Large-tree scans declare budget and cancellation behavior; disk headroom is checked before staging. Quarantine directories keep every replaced byte and are never cleaned up automatically in v1 — deleting them is the user's choice, trading the foreign branch for space.

**Restore transaction.** Restore is journaled and resumable, with an explicit commit point. Replacement files are staged under `*.tmp` names inside the target directory and synced before being published: canonical `session[.vN].jsonl.zstd` names only ever hold complete files, because cross-directory moves are renames and copies land under a temporary name first. The transaction acquires the session's own `session.lock`, persists a journal (target session, checkpoint id, phase, pre-state file fingerprints) before touching live files, then applies by moving live generation files to quarantine and renaming staged files into canonical names — every intermediate set stays coherently selectable because the reader picks the highest canonical generation and canonical names are never half-written. The journal commits (file and directory sync) *before* the lease is released. Finalize is still journaled work: invalidating the restored session's `session_projcache` rows — the per-record documents and the row inside the legacy whole-unit file the backend replays when the tree is empty, for the target and its related-source closure — runs after the switch but must complete, idempotently, before the journal is deleted and before the next Host spawn. A missing or malformed legacy file is left alone; other legacy-cache read failures retain the committed journal for retry. A leftover committed journal is never re-applied, because the file switch must not repeat, but it is always finished. The no-other-Harness precondition spans the whole transaction, not just the switch: foreign instances stay quit from restore start until finalize is durable, so the legitimate window for foreign writes to the restored log opens only after the journal is deleted — an external Host starting between commit and finalize would otherwise load the stale cache rows. A leftover journal's resume re-establishes the precondition rather than inheriting the earlier confirmation: it runs at the same pre-Host lifecycle point and re-acquires the lease, and a pre-commit journal additionally re-stats live files against the recorded fingerprints — when a foreign writer appended during the interruption, it stops at that member and names the journal and quarantine location. Earlier members may already be restored; the conflict notice does not promise an untouched closure. Resume needs checkpoint bytes only while the journal is still in `intent`: a `committed` or `finalized` leftover converges even after its checkpoint is pruned, while an `intent` leftover whose checkpoint is gone can never finish the switch — startup names that journal unresolvable and offers an explicit abandon-or-keep choice instead of deferring it forever. Durability ordering: the staged checkpoint directory tree syncs from leaves to root before publication; newly created journal and quarantine ancestors sync through the home; the switch intent is persisted before files change; file contents sync before their rename publishes them, both parents sync after quarantine moves, and live directories sync before `committed` is recorded; `finalized` is recorded after cache invalidation durably completes, and the journal is deleted last — on Windows staged contents flush through writable handles, while directory fsync is unavailable. Quarantine and checkpoint live under the same `$DSH_HOME` volume as `sessions/`, keeping renames atomic; a cross-device home copies to a quarantine temporary, verifies and flushes it, publishes and syncs the destination, then unlinks and syncs the source. Resume recognizes identical fingerprinted live and quarantine copies left before source removal and finishes the move without treating them as a foreign write.

**Confirmed restore targets.** A restore confirmed while the local Host is up cannot run in place, so the intent is persisted to `electron/pending-restore.json` and executes after a relaunch, inside the same pre-Host window as journal convergence; each queued request records the confirmed checkpoint id and a stable operation id copied into the journal. A finalized journal durably acknowledges that exact request before deletion; an interrupted acknowledgment retains the journal for resume, and the queue never starts another transaction for a request already owned by a journal. A newer request for the same session is preserved. A missing queue file means no pending requests; other file-read failures reject listing, enqueue, and dequeue without changing the queue. Startup restores also use the checkpoint shown in the confirmation. A missing target, including a legacy queue entry without a checkpoint id, is refused rather than redirected to a newer checkpoint. Journal convergence runs before maintenance and again afterward, including when maintenance throws: a new unfinished transaction reaches the same retry, explicit-continue, or quit decision before Host startup. Decisions are remembered for the same journal bytes and convergence outcome during one launch; the second pass prompts only for new or changed states. Unreadable or unsupported-version journals also require this decision, and journal-directory read failures cannot masquerade as an empty directory.

**Live related sessions.** Before recording a new restore intent, and before resuming an interrupted intent, restore holds every selected member lease and compares current backend headers with the physical generation-file directories. A live subagent child of any selected member must already belong to the confirmed restore set; otherwise restore refuses before changing session history, and an interrupted intent remains deferred. Selected members retain their immutable checkpoint or journal headers when newer generations make backend listing skip them. Any other generation directory omitted by listing has unknown parentage and also blocks recovery, including when that directory might be unrelated. Readable unrelated sessions remain untouched. Close other Harness instances throughout inspection and switching.

**Concurrency.** Restore acquires the target session's `session.lock` through the backend's leasing mechanism — a successful acquire proves no live writer, contention refuses cleanly, and holding it through the swap closes the probe-then-move race. Files are replaced inside the kept directory and lock file, preserving lock identity on both platforms. A session with no verified checkpoint copy is refused outright and left in place — v1 does not move live data it cannot replace, and a standalone quarantine feature would need its own mutual-exclusion design. Readers sit outside the lease guarantee at two depths. The shallow one: read opens take no lease, so a foreign reader mid-swap can observe a transient missing or partial generation set and must retry — the bundled Harness never reads during restore because the Host has not spawned or is relaunching. The deep one: a foreign Host keeps in-memory projections of the pre-restore log, and its `coldSnapshot` write-back is fire-and-forget — a reader that fetched the old log before restore can resurrect a stale `session_projcache` row after our invalidation, while cache identity (`formatVersion`, `createdAt`, `cwd`, `inheritedEventCount`) cannot tell the rolled-back log from its polluted successor. Neither the lease nor the row delete covers this, so v1 hardens a precondition it already needed: restore executes only while no other Harness instance is live, for the whole window from switch start through persisted finalize — writers are detected through the lease, readers leave no trace, the confirmation requires keeping other `dsh`/Rivetdeck instances quit for that span, and the restore entry refuses while the local Host is up. A cache epoch inside `CheckpointIdentity`, letting stale write-backs be rejected, is a post-v1 upstream change. The Windows semaphore cannot be treated as rename isolation — it holds no file handle.

**Profile restore is separate and post-v1.** The profile affects every session, so it cannot roll back implicitly with one session. Its restore is a distinct transaction: the managed file set above plus the home patch, applied under the shared profile writer lock (`withFileLock` on `package.json` precedent), with dependency rebuild honoring `pnpm-lock.yaml` through the bundled package manager — the current `prepareCoreProfile` path returns early when `package.json` exists and cannot serve — and a fallback that puts the previous files back when install fails, including a `node_modules` tree already mutated by the failed install. v1 backs up these files but does not claim mode C coverage.

**Restore scope honesty.** Restoring a session does not restore the surrounding world: workspace files, external tool side effects, and plugin stores outside the covered set keep their newer state, and a persisted schedule may still deliver into a restored session. The confirmation UI names the oldest capture time among the target and its transitive subagent members, warns that each member loses changes after its own capture time, and gives the quarantine location and these limits; whether the first launch after a restore may immediately run background tasks stays deferred in the Agent Note.

**Semantics to communicate.** Restore rolls back; it does not merge. Events written by the newer harness become invisible to the bundled build (recoverable by swapping the quarantine back), and if the bundled build then writes to the rolled-back session, the histories diverge permanently — the format gives no fallback path from a successor generation to its predecessor.

<a id="limits-and-risks"></a>

## Limits and risks

1. Rollback, not merge — see the semantics paragraph above; two writers fork a session permanently.
2. The checkpoint must exist before the pollution; already-affected sessions have no pre-image.
3. A concurrent foreign write during a Desktop run stays unpromoted only when per-session validation catches it; validation is the load-bearing gate, stat-diff is not.
4. The covered set is a whitelist; future `$DSH_HOME` state kinds need manifest updates.
5. The lease protects writers that honor it; a foreign reader mid-restore can see a transient partial set and must retry — accepted, because foreign reads racing file-level maintenance are already possible today. A violating process's in-flight `coldSnapshot` write-back can still re-poison `session_projcache` after a restore that ran without the no-other-harness precondition — the precondition, not the lease, is what closes that path.
6. Scope covers only the Desktop application's flow; a CLI-only user hitting the same skew has no recourse here — the upstream "no plugin-side fix" conclusion stands.
7. Stat-diff flags any foreign write, including fully compatible ones; the confirm-by-parse step in detection keeps prompts precise.
8. Crash or force-quit promotes nothing; the previous verified checkpoint remains, so a restore can drop a whole run's session growth.
