## Current uninstall behavior

The downstream Windows installer is an assisted NSIS build (`oneClick: false`, `allowToChangeInstallationDirectory: true`, ZIP payload) produced by `apps/electron/scripts/prepare-windows-installer.mjs`. On Windows packaging hosts the script compiles `installer/uninstall-data.cpp` into `rivetdeck-uninstall.dll` (`scripts/prepare-windows-uninstall-helper.ps1`), projects the stock templates with the `--delete-app-data` `RMDir /r` bypass stripped, and emits `customInstall`/`customUnInstall` macros plus LangStrings generated from `installer/uninstall-messages.yml`.

Each packaged launch merges the resolved `userData` and `DSH_HOME` into a line-oriented record beside the default userData (`src/path-history.ts`, `%APPDATA%\rivetdeck-path-history.ini`) before the fallible startup steps run, so a launch that fails during network or runtime preparation still leaves its roots on record. The record is outside the installation directory and writable without installation privileges. A cross-process writer lock covers each read-modify-write cycle, so concurrent launches with different `userData` roots retain every claim within the current installation. A real uninstall appends `retired=1`: readers discard that installation’s `userData` cleanup candidates and completeness while retaining all `DSH_HOME` and unknown protection claims. The next launch records only its current `userData` root with incomplete history. An installer with no prior uninstall registration also retires any surviving record before writing registration; retirement failure stops installation, and uninstall reports retirement failures. Updates and replacements preserve the active record unchanged. If it cannot be read or updated, startup reports the error and stops before initializing services or opening the Harness home. Only installs with no prior registered installation, no surviving default `userData` root, and no updater cache seed `complete=1`; this seed attests only the default `userData` root checked by the installer. Discovering an unrecorded non-default root makes history incomplete, even when the root carries product markers, because its earlier Harness homes are unknown. Returning to a recorded or default root does not restore completeness. Upgrades and reinstalls over surviving user data or updater caches also seed an incomplete record.

On uninstall, `customUnInstall` calls `un.RivetdeckCleanData`, which keeps all data when the uninstaller runs for an update (`--updated`) or a same-product replacement (`/KEEP_APP_DATA`); the record beside the default `userData` is outside `$INSTDIR`, so it already survives for the succeeding install. Otherwise the flow resolves the current `userData` root (`$APPDATA\Rivetdeck`), the updater cache (`%LOCALAPPDATA%\rivetdeck-updater`), the environment `DSH_HOME`, and the record, and hands them to the native `UninstallCleanup` entry point (exported by `installer/uninstall-data.cpp`; policy in `installer/uninstall-cleanup.h`). The helper applies the layered policy: `managed-toolchains/`, `electron/toolchains/bin`, named cache directories including per-partition equivalents, and the updater cache are removed after ownership and expected-inventory checks; `desktop-preferences.json`, `network-secrets/`, `network-startup-override.json`, and persisted browser storage stay. `--delete-app-data` removes the whole `userData` root only while the record is present and complete. Named caches, managed runtime trees, and the updater cache require complete history; otherwise they stay whole because their inventories cannot exclude an unrecorded Harness home in an arbitrary subtree. Protection includes both the recorded path and its resolved junction or symlink target; inaccessible or broken links block cleanup. Targets that fail verification or overlap a protected path are skipped whole; skips and removal failures land in `%APPDATA%\Rivetdeck-uninstall-residue.log` and the uninstaller details page. Enumeration errors reject partial inventories, and a path whose existence cannot be queried is reported with its error rather than read as absent. Cleanup errors and helper-call failures also display localized warnings; a failed report write shows the Windows error and skipped-target count without linking to an unusable report.

The macOS DMG/ZIP and Linux AppImage artifacts ship no uninstaller; the DEB removes only `/opt/Rivetdeck`. The MSIX (Store) build is removed by the operating system including virtualized per-package data, but non-virtualized pre-existing files persist, and `~/.dsh` is outside virtualization — see "Known limitations" for the verification gap.

## Write locations and ownership

Every write root needs an explicit owner and cleanup policy:

| Root | Contents | Owner and policy |
| --- | --- | --- |
| `$INSTDIR` | Program files, `resources/core-runtime` (Windows `node.exe`), `resources/network-runtime` | Installer — already removed |
| `userData/managed-toolchains` and `userData/electron/toolchains` | Downloaded Node/Python generations, receipts, staging, shims | App-private, fully rebuildable — primary cleanup target |
| Chromium cache directories in `userData` | `Cache/`, `Code Cache/`, `GPUCache/`, `DawnGraphiteCache/`, `DawnWebGPUCache/`, and their per-partition equivalents | App-private, rebuildable — cleanup target |
| `userData` (remainder) | `desktop-preferences.json` (proxy config, update channel, runtime onboarding), `network-secrets/` (usable encrypted proxy credentials), `network-startup-override.json`, `electron-host.patch.yml`, persisted browser storage (cookies, Local Storage, IndexedDB, and other session-partition data) | App-private settings, credentials, and user content — preserved by default |
| Updater cache | Downloaded update packages | App-private, rebuildable — cleanup target |
| `$DSH_HOME/electron` | `python-user/` and `node-global/` user-installed packages, `bin/` shims, `host-profile/`, markers | App-private subtree inside a shared home — the uninstaller must not remove it; contents include user-installed packages, not cache |
| `$DSH_HOME` (remainder) | Sessions, storages, settings, `.credentials.yaml`, web profile, plugins, caches | Shared Harness home — `dsh` CLI and other consumers share it; never remove automatically |
| `~/.agents` | User-level skills shared across agent tools | Shared — never remove automatically |
| Workspace directories | User projects | User — never remove |

`userData` is relocatable via `--user-data-dir`, and `$DSH_HOME` via the `DSH_HOME` environment variable. The uninstaller cannot discover these overrides from its own environment alone; see "Path history and protection".

## Path history and protection

"Never delete `$DSH_HOME`" is only enforceable because the uninstaller knows which directories the app actually used; the uninstall process's own environment cannot answer that, since a launch script can set `DSH_HOME` transiently and `--user-data-dir` relocates the root holding managed runtimes. The mechanism:

1. **A persisted history set of effective roots.** Each launch merges the resolved `userData` and `DSH_HOME` paths into a durable record rather than overwriting the previous entry: a Harness home used for an earlier launch and later switched away stays protected. The record lives beside the default userData — a per-user location the uninstaller can read without the app's launch environment and that a normally-privileged app can always update. It tracks its own coverage: one first created after an upgrade cannot attest which roots ran before it existed, so it carries an incomplete-history state that keeps conservative skipping instead of pretending the history is whole.
2. **Separate roles for recorded paths.** Historical `DSH_HOME` entries always join the protection set. Historical `userData` entries locate and verify cleanup candidates; they are never protection by themselves — their settings and persisted storage survive through the same tiered policy that preserves them in the current root.
3. **Deletion candidates verify attribution.** A deletion target must be attributable to this product and match its expected inventory — for example `desktop-preferences.json` or `managed-toolchains/{node,python}/active.json` — never trusted from the path string alone.
4. **Protected paths need no attribution.** A recorded `DSH_HOME` joins the protection set unconditionally; a shared Harness home may contain no Electron markers at all. A malformed or unresolvable record does not drop a protection claim — it blocks every deletion whose safety cannot be proven without that record.
5. **Safety is proven, not assumed.** "No overlap found" is not "no overlap exists": a missing or incomplete history record means a past `DSH_HOME` inside `userData` cannot be ruled out, so absence of evidence does not authorize deletion. Each deletion target must prove its isolation — full `userData` removal under `--delete-app-data` requires a complete history record attesting that no protected path ever lived inside; inventory-checked tiered targets must match their expected contents, and foreign content skips the whole target rather than being emptied with it. Named caches, runtime generations and staging, and updater staging have no closed inventory, so incomplete history leaves their entire cleanup targets intact and reports them. Any target that overlaps a protected path — recorded or environment-derived — is likewise skipped entirely, with the skip reported in the residue. Installs that predate the record — or whose record reports incomplete history — use environment plus defaults for protection and apply this same proof requirement, which limits them to targets that verify cleanly.

## Deletion rules

1. No data is deleted during an update (`isUpdated`) or during a same-product uninstaller replacement (`/KEEP_APP_DATA`); these protections take precedence over any deletion request, including `--delete-app-data`.
2. All deletion outside `$INSTDIR` goes through the native helper ported from upstream's `uninstall-data.h`, with its safety tests. The stock `--delete-app-data` `RMDir /r` bypass is stripped from the generated templates — fixed file names are not a defense, because a parent directory in the chain can itself be a junction.
3. Protected roots and any target containing or contained by `$INSTDIR` or the resolved `DSH_HOME` are rejected.
4. Targets are honored through the persisted path record, `--user-data-dir`, and `DSH_HOME`; a target that cannot be resolved or verified is declined, and a target that cannot be queried is reported rather than read as absent.
5. Cleanup is best-effort, not a no-residue guarantee: locked files held by a still-running Host or agent subprocess are skipped and reported observably instead of failing the uninstall mid-delete. "Tolerates locked files" and "leaves no residue" cannot both be promised; the contract is best-effort removal with reported residue.
6. Credentials-bearing and user-content roots (`$DSH_HOME` including `electron/`, `~/.agents`, workspaces) are never removed under any uninstaller flag.

## Other platforms

Only Windows has an uninstaller. The macOS DMG/ZIP and Linux AppImage artifacts remove no data; the DEB removes only `/opt/Rivetdeck`. Per-platform manual cleanup lists live in the [user cleanup guide](user/cleanup-user-files.md). The MSIX (Store) build is removed by the operating system including virtualized per-package data, but non-virtualized pre-existing files persist and `~/.dsh` is outside virtualization — parity is unverified (see "Known limitations").

## Known limitations

- Application data is per-user even under an all-users install. Uninstalling under a different account than the one that used the product only reaches that account's `userData`, updater cache, and history record; other users' roots remain until each of them uninstalls or removes them.
- Builds predating the `Rivetdeck` product name wrote `%APPDATA%\DeepSeek Harness`, a root no history record can name, so the uninstaller never reaches it. Removing it is a manual step.
- Chromium directories outside the named cache list — `Crashpad`, `Service Worker`, and other diagnostic or registered-state directories — stay behind after tiered cleanup; they leave the root only under `--delete-app-data`.
- MSIX uninstall parity is unverified: the OS removes the package and its virtualized file data, but Microsoft distinguishes virtualized files from pre-existing non-virtualized ones, which can persist. Current Store smoke only confirms package unregistration, and runtime smoke uses a custom `userData` outside the package, so the default toolchain location's fate under Store uninstall is unknown; a first-time Store install, a Store install over existing NSIS data, and a Store install with custom external paths must run before parity is claimed.
